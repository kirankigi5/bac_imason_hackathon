# Railway Deployment

Prepared October 4, 2026. Nothing has been deployed, pushed or published by this
deployment task. Ranking, scoring, data, APIs, providers and UX are unchanged.

**Public exposure is not safe yet.** Saved-project APIs and server actions use a
shared, unauthenticated SQLite database. Decide on access protection before
generating a public domain. The recommendation below is not implemented.

## Deployment Contract

The repository-root Dockerfile builds the existing `apps/web` application with
`npm ci`. It uses Node 22 on Debian, preserving built-in `node:sqlite`. The final
image contains production dependencies, `.next`, public assets and startup tools.
The current Next.js configuration is unchanged: conventional `next start`, not
standalone output. The wrapper drops root privileges after preparing the volume.

No `.env.local`, host build output, source datasets, user database, runtime data
or seeds are copied into the image. MapLibre assets are regenerated by the
existing build script. Supply credentials only in Railway's Variables UI.

One persistent volume must be mounted at `/app/runtime`:

```text
/app/runtime/
  feature_store/
    manifest.json
    releases/ec0ed269269ed0f45e5b/
      manifest.json
      location_features.json
      evidence/county-*.json
  projects/
    projects.sqlite
    projects.sqlite-wal       (created as needed)
    projects.sqlite-shm       (created as needed)
```

Railway mounts volumes at startup, not during builds or pre-deploy commands.
Consequently restoration runs in `scripts/start_railway.sh`, before Next starts.
[Railway volume guidance](https://docs.railway.com/volumes).

Keep one service instance. Railway volumes do not support replicas, and attached
volumes entail brief redeployment downtime. Allow at least 0.5 GB for the 124.82 MB
runtime store, temporary extraction and growing project state; monitor usage and
increase capacity as needed. Root entry prepares ownership, then runs as `node`.
[Volume limits and permissions](https://docs.railway.com/volumes/reference).


This command publishes a Release and creates its tag if absent. Do not run it
until ready to publish. For an existing tag/release, verify its target and upload
with `gh release upload "$TAG" "$ASSET" "$ASSET.sha256" "$ASSET.metadata.json"
--repo "$REPO"`; never overwrite an immutable asset with different bytes.
[GitHub CLI release instructions](https://cli.github.com/manual/gh_release_create).

Alternatively, GitHub -> Releases -> Draft a new release: use the tag above,
select the pushed commit, attach the three files, retain the attribution notice,
then publish. A draft asset is not an anonymous production download.

Only after the asset exists, obtain its actual download URL:

```bash
gh api "repos/$REPO/releases/tags/$TAG" \
  --jq '.assets[] | select(.name == "runtime-data-ec0ed269269ed0f45e5b.tar.gz") | .browser_download_url'
```

Paste that returned URL into Railway `RUNTIME_DATA_URL`, not a guessed URL.
It must permit an anonymous HTTPS download. Private GitHub release assets
require authentication, which this restore implementation does not add. If the
repository is private, choose an authorized publicly readable release location
or object-store URL; do not embed GitHub tokens in URLs or container layers.
Keep the immutable asset available for future volume recovery.

## Railway Steps

1. Create a new Railway project. Start with an empty project so configuration
   can be completed before the first deployment.
2. Connect the existing GitHub repository to a service. Authorize the Railway
   GitHub integration and select the intended pushed branch. Do not enable
   public networking yet; pause/cancel any automatic first deployment while
   configuring the service.
3. Configure the service's root as the repository root, **not `apps/web`**.
   Use the root `Dockerfile` and `railway.toml`. Start command is
   `sh /app/scripts/start_railway.sh`; leave pre-deploy empty. Keep one instance.
4. Add a persistent volume to this same web service.
5. Set its mount path to `/app/runtime`. Do not mount it over `/app` or
   `/app/apps/web`. The wrapper rejects Railway startup without this volume.
6. Add the non-secret environment variables from the table below in the service
   Variables UI. Railway supplies `PORT`; the server binds `0.0.0.0:$PORT`.
7. Add `GEMINI_API_KEY` as a server-side Railway secret/variable and `LLM_MODEL`
   as your account-supported Gemini model. Never paste `.env.local` into Git,
   upload it as an asset, or use `NEXT_PUBLIC_*` for provider settings.
8. Set `RUNTIME_DATA_URL` to the actual published archive URL and
   `RUNTIME_DATA_SHA256` to the verified checksum above. The first restore
   requires both; there is no checksum bypass.
9. Deploy the configured service. Check startup logs for `runtime_data=restored`,
   `public_data`, the expected release, 3,109 counties and passing startup
   validation. JSON logs represent these as fields, not literal equals signs.
10. **Only after approved access protection is implemented and verified**, use
    service Settings -> Networking -> Generate Domain. No public-demo security
    mechanism is included in this preparation. Keep it private otherwise.
11. Verify the active release using the server-side command below. The existing
    GET `/api/project/status` is Railway's lightweight readiness route.
12. Run the production smoke test below. Save a non-sensitive test project,
    restart the service, and confirm its criteria and revision history remain.
    Never delete the persistent volume to redeploy application code.

The Docker build and start configuration is declared in
[railway.toml](../railway.toml), following
[Railway Dockerfile guidance](https://docs.railway.com/builds/dockerfiles).

## Startup And Verification

The wrapper requires explicit valid provider configuration and absolute persistent
paths. It prepares directories, gives the volume to `node`, restores or validates
runtime data, checks SQLite read/write integrity in a rolled-back transaction,
and checks that configured credentials are absent from client JS. It then
executes the existing production Next server directly for signal handling.

Restoration is once per startup, not per request. Valid existing data is fully
validated and reused without downloading, even if the URL is unavailable.
Absent/invalid data requires URL and checksum. The download uses a temporary
`.part`, bounded download/expansion sizes, rejects unexpected paths and archive
links, and verifies pinned manifest, features and county evidence hashes before
an atomic rename on the volume. A replaced invalid store is preserved as
`feature_store.invalid-*`; inspect it before removing it manually. Failed
download/checksum/extraction leaves active data untouched and startup fails.
The production wrapper never accepts `seeded_demo` or builds the data pipeline.

After deployment, link the Railway CLI to the actual project/service, then run:

```bash
railway login
railway link
railway ssh -- node /app/scripts/verify-deployment.mjs
```

[Railway SSH command reference](https://docs.railway.com/cli/ssh).
Expected output includes `verification: passed`, `data_mode: public_data`,
release `ec0ed269269ed0f45e5b`, `county_count: 3109`, SQLite writable,
client credentials absent, provider `gemini`, and ranking passed. The probe
checks backend ranking and a matching county evidence trace; it does not train
anything, compute replacement scores, save projects or call Gemini.

For an externally accessible, appropriately protected demo:

```bash
# Substitute the actual domain after it exists; no hosted URL is created here.
APP_URL=https://YOUR_ACTUAL_DOMAIN npm run verify:deployment -- --http-only
```

This mode checks existing HTTP ranking/trace/status endpoints only; it cannot
claim remote filesystem writability. An access gate must allow the operator's
authorized requests; this probe does not yet supply future gate credentials.
Run the server-side check through Railway SSH while the service remains private.

GET `/api/project/status` makes no paid provider call; `unverified` provider
health is normal until an explicit provider verification. Do not use its POST
method or the paid conversation/explanation routes as ordinary healthchecks.
Railway's healthcheck gates deployment readiness, not continuous monitoring.
[Railway healthcheck behavior](https://docs.railway.com/deployments/healthchecks).

For the manual production smoke test, open a complete project, verify map and
rankings, select a county and inspect evidence, then save/reopen the test project
after a service restart. Avoid live LLM verification unless explicitly intended;
ordinary probes above do not charge the provider. Retain volume backups before
updates. Back up SQLite consistently (a quiesced service/volume backup or SQLite
backup API), not an isolated copy of a live DB while ignoring its WAL.

## Public Demo Decision

| Option | Assessment |
| --- | --- |
| A. Server-side shared demo access protection | Recommended smallest hackathon change; protect page, APIs and server actions together, keeping the existing SQLite workflow. Trusted participants still share project state. |
| B. Isolated session project state | Better isolation, but requires session identity, ownership and request/storage changes. Larger than deployment preparation. |
| C. Disable saved persistence in public mode | Reduces shared-state exposure but changes the saved-project UX and does not by itself prevent unauthenticated paid LLM use. |

Recommendation: implement A in a separately approved pass, with a server-only
credential, HTTPS, protection for direct API/server-action access and reasonable
request limits. Keep only the non-sensitive GET status endpoint available for
Railway readiness if needed. A shared password is a limited trusted-judges demo
option, not multi-user authorization; use only non-sensitive test projects and
set provider quotas. Do not expose an alternate unprotected origin.

**No option is silently selected or implemented here.** Public internet exposure
remains blocked on this decision. A future wider launch needs authentication,
authorization, abuse controls and an appropriate persistence strategy.
